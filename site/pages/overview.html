Agent Liaison Protocol · version 0.1 draft

Between people, through their agents.

The Agent Liaison Protocol (ALP) is an open standard for work between people, carried by their agents, under each person’s rules.

At a glance

What it is
An open standard for work between people, carried by their agents, under each person’s rules. Each agent talks only to its own person’s home broker, which is to the agent what a mail server is to a mail client, and brokers carry only what both people’s rules allow.
Status
Version 0.1, a draft for implementers. One implementation, the reference broker in this project; we know of no implementation outside this project. Real agent products were tested together once, on November 7, 2026, with test identities. Status.
Who it is for
Organizations and people whose members use agents from different vendors, and those who build agents and agent platforms.
Who is behind it
Brien Collier at Lucaryin wrote ALP. Lucaryin is its initial steward and the licensor of the reference broker, and intends to move the specification to a neutral foundation. No foundation has agreed to host it yet, and no vendor, foundation or standards body has endorsed it. About the project.
What it costs
Anyone can implement ALP without asking, including in a broker of their own that they sell. The reference broker is free for any organization to use, modify and run for itself, under its license.
Agreements needed
None to implement it. Implementing ALP needs no agreement with Lucaryin. Nor does using, running or modifying the reference broker for any purpose its license permits.

The problem

An analyst preparing a quarterly review needs the priorities of the leader she reports to, and an hour on his calendar. Her agent and his come from different vendors. Three things go wrong at once:

  • Data leakageHer agent’s request shouldn’t carry her draft numbers, and his agent shouldn’t answer with more than he would share.
  • Access sprawlHer agent shouldn’t need a login to his calendar, mailbox or documents to get an answer.
  • ImpersonationHis agent shouldn’t respond to anything that merely claims to be hers.

Three guarantees

In ALP, agents never talk to each other directly. Each talks only to its own person’s home broker, and brokers keep three promises:

  1. Nothing crosses that both people’s rules don’t allow. Each message type’s schema classifies every field, and a field crosses only if the sender’s permissions, each side’s organization policy and the recipient’s rules allow it. Free text is off unless the recipient opts in, capped at 280 characters, checked for sensitive data and labeled untrusted.
  2. No agent gets into another person’s accounts. Each agent signs in only to its own person’s broker and never holds another person’s tokens, cookies or sessions.
  3. Senders are proven, not claimed. Identity is proven by the sender’s domain and home broker, never by the message. Strangers can only send a connection request, which goes to the person, not the agent.

What ALP can’t do. These hold on the ALP channel: nothing leaves a person’s side that their rules don’t allow, and nothing reaches their agent from anyone they, or their organization’s policy, haven’t approved. ALP can’t control what a vendor’s agent does with what it reads, or how a vendor stores it, and a stolen sign-in or a compromised broker can still speak for its own people until it’s revoked.

What your organization would do

A person
Adds one connector to their agent and signs in, then approves connection requests and commitments on their own approvals page. Connect an agent.
An IT or security team
Runs a broker for the organization’s own people, signs people in through the organization’s identity provider, and sets its private policy: default relationships, which agents may connect, retention and kill switches. Run a broker.
An agent provider
Builds the client side into its agent, and can run its own broker for addresses on its own domain. Where to start reading.

The reference broker is new code and has not had an independent security review (status).

What happens to your data

  • What leaves a person’s side: only fields both people’s rules allow, checked by the sender’s broker before anything leaves and by the recipient’s before anything is delivered.
  • Who sees messages: both home brokers, in plaintext, because they must read fields to enforce rules, and each agent’s vendor, for whatever reaches its agent. There is no end-to-end encryption in v0.1.
  • What each ledger records: what crossed, the scope, the fields disclosed and every decision. Free text and notes are kept in a separately encrypted payload by default, and typed values only where the organization allows.
  • Who can read a ledger: the person, at any time, and the organization’s compliance roles, as its policy allows.
  • Where a broker runs: on an organization’s own servers or inside its workspace platform. The specification also defines hosted brokers, which a third party runs under a published operator statement (Sections 3.3 and 13.9); the repository’s note on a hosted deployment says: “Nothing has been deployed this way.”
  • What ALP can’t control: what a vendor’s agent does with what it reads, or how a vendor stores it.

From the specification’s Section 1.4, Section 11 and Section 15.

Two ways in

Client mode: no vendor work

A person adds one custom connector to the agent they already use and signs in with their own account. The broker enforces the rules, so the guarantees hold though the vendor did nothing.

Native mode: the vendor builds it in

A vendor’s agent includes the client side itself, so no connector is needed. Both modes share addresses, messages, permissions and ledgers.

ALP and other protocols

MCP connects agents to tools. A2A connects agents to agents. ALP connects people through their agents, under each person’s rules.

Poppy (the Personal Agent Protocol) is for a person’s agent and a business; ALP is for work between people. The test is the counterpart: a business’s service that any customer uses means Poppy, and a named person or role with its own ALP address, reached under both sides’ rules, means ALP. Try it

This needs a developer and Node 22.18 or later.

git clone https://github.com/AgentLiaisonProtocol/agentliaisonprotocol alp && cd alp/reference
npm ci            # Node 22.18 or later
npm run demo      # the whole story, over real HTTP on your machine
npm test          # the test suite, including every conformance vector

Or read what the demo prints. The quick start has two other ways in.
