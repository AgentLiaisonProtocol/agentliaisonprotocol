# Claims and their evidence

Every claim the [README](README.md), the [announcement](announcement/introducing-agent-liaison-protocol.md) and the [bridge kit](bridge-kit/) make about the Agent Liaison Protocol (ALP), with the evidence for it: a section of the [specification](spec/alp-v0.1.md), a [conformance vector](vectors/), a test or demo step of the [reference broker](reference/), a vendor page listed in [bridge-kit/SOURCES.md](bridge-kit/SOURCES.md), the test with real agents on November 7, 2026 ([bridge-kit/README.md](bridge-kit/README.md#tested-with-real-agents)), or the test against a live Microsoft Entra tenant on November 8, 2026 ([SELF-HOST.md](SELF-HOST.md#tested-against-a-live-entra-tenant)); the records of these two tests aren't in this repository. A row marked **limit** states what the claim does not cover. Checked on November 8, 2026, against this repository: every cited file, section and demo step, with the tests and demos passing. "Approvals page" is the person's page on their broker (the specification's web view).

Test files are under `reference/src/`; "demo step N" is a step of `npm run demo`.

## What ALP guarantees

| Claim | Evidence | Limit |
|---|---|---|
| On the ALP channel, nothing leaves a person's side that their rules don't allow. | Spec 6.6 (sender-side evaluation, S1 to S8); `vectors/policy/sender.json`; `core/broker.test.ts` (Act 1); demo steps 2 and 7b | Typed fields are checked field by field; allowed free text is only as good as the DLP hook (spec 6.9). |
| Nothing reaches a person's agent from anyone they, or their organization's policy, haven't approved. | Spec 6.1, 6.2, 6.7; `vectors/policy/recipient.json` (a stranger's message becomes a contact attempt); demo step 4 | Organization default relationships (spec 6.4) approve on the person's behalf. |
| A field crosses only if the sender's permissions, each side's organization policy and the recipient's rules allow it. | Spec 6.6, 6.7; both policy vector files | |
| Free text is off unless the recipient opts in, capped at 280 characters, checked for sensitive data and labeled untrusted. | Spec 7.3 and 8.2 (the 280-character cap), 6.5 (coverage by exact pointer), 6.9, 12.1.6; `vectors/delivery/sanitize.json`; demo step 7c (`dlp_blocked`) | Sanitizing removes the cheapest tricks; it is not protection against prompt injection (spec 1.5, 14). The reference runs a sample pattern check (payment cards, private keys, credentials, US SSNs); connecting an organization's DLP service is code (`DlpHook`, spec 6.9), and `npm start` refuses a policy whose `dlp.hook` names one. |
| A sending agent can add at most four labels, each one the scope or its organization's rules already name exactly, so added labels can't carry made-up text. | Spec 6.5; `vectors/policy/sender.json` (an unknown label, a made-up label below `confidential.*` and a fifth label are refused); `core/review-hardening.test.ts` | **Limit:** the agent's choice among named labels still carries a few bits per message. |
| No agent gets into another person's accounts: each signs in only to its own person's broker and never holds another person's tokens, cookies or sessions. | Spec 5.5, 5.6; `oauth/oauth.test.ts` (audience-bound tokens); `mcp/binding.test.ts` (another principal's token can't act as Ana) | ALP can't stop an agent from using its own person's other tools. |
| Identity is proven by the sender's domain and home broker, never by the message (senders are proven, not claimed). | Spec 5.1, 12.2.4; `vectors/federation/acceptance.json` (rogue broker, wrong authority, unpinned key); demo step 3 | A compromised home broker can sign for its own principals, and a stolen sign-in acts for its person, until revoked (spec 14). |
| A broker the domain document no longer names stops speaking for that domain's people. | Spec 4.5, 12.2.4 steps 3 and 6; `core/review-hardening.test.ts`; `npm run demo:federation` | Within the document's `max_age` (at most 24 hours, 1 hour recommended). |
| Strangers can only send a connection request, which reaches the person, not the agent. | Spec 6.2; demo steps 4 and 7f | |
| A connection request gets the same answer whether or not the address exists. | Spec 6.2.2; `vectors/federation/connection-requests.json`; `core/review-hardening.test.ts` | Latency is comparable, not identical. |
| Short-lived, audience-bound tokens with rotating refresh tokens, or a revocable personal access token of at most 30 days for organization accounts. | Spec 5.6, 5.7; `oauth/oauth.test.ts`; `mcp/binding.test.ts` | Bearer tokens, not sender-constrained: current agent platforms don't support DPoP (spec 5.6 item 11). |
| An organization can forbid personal access tokens. | Spec 5.7, 6.10: leave `pat` off the `clients` list in `enforce` mode, and the broker mints none and refuses those already issued; `web/web.test.ts` | |
| A person signs in with their own account, and again each time the connector grant ends. | Spec 5.6 item 7 (at most 30 days for organization principals, 90 for others) | |
| Revocation is immediate on the revoking broker, and within the cache bound elsewhere. | Spec 6.2.4, 4.4, 5.8; `npm run demo:federation` (revocation); `core/review-hardening.test.ts` (kill switches stop reads); `oauth/oauth.test.ts` (a revoked connection's access token stops working) | |
| Kill switches on an agent, a person or an agent product stop reads as well as sends; on a scope or an outside domain they stop new messages. | Spec 5.8; `core/review-hardening.test.ts`; `oauth/oauth.test.ts`; `policy-files.test.ts` (`SIGHUP` applies a kill switch in one policy file whatever happened to the others) | Messages already delivered in a blocked scope, or from a blocked domain, stay readable. |
| Notifications only notify. | Spec 12.5.1; demo steps 0b and 8; `web/web.test.ts` | **Limit:** the reference broker prints each notification and writes it to an outbox file; it sends no email or SMS yet. |
| Approvals happen on the person's approvals page with a fresh sign-in. | Spec 9.4, 12.5; demo step 7h; `oauth/oidc.test.ts` (the single sign-on step-up); the test against a live Entra tenant ([SELF-HOST.md](SELF-HOST.md#tested-against-a-live-entra-tenant): two approvals, each with a fresh Entra sign-in, recorded as `sso-stepup`); `web/hosted.test.ts` (passkeys) | **Limit:** with test identities the reference re-checks a test sign-in (`reauth-dev`). With an organization's identity provider it does a single sign-on step-up on the loopback page: a fresh sign-in at the provider for each approval, whose nonce is a hash over that action and what it covers; built and tested against a standard OIDC provider, and once against a live Entra tenant with test users. Served on its public origin (`ALP_WEB_PUBLIC=1`, people signed in by invite), it asks for a passkey with user verification whose challenge carries the hash of the terms (`webauthn-uv`). |
| Binding commitments need both people to ratify the agreed terms, unless a person gave approval in advance. | Spec 9.4 (standing ratification within a grant's `limits`); `vectors/threads/meeting-commit.json`; demo step 7h; `mcp/commit.test.ts` (a relationship set up through a connection request with the default terms reaches commit once both people ratify; in `alp.document_request/1` only the proposer commits) | |
| Both ledgers record what crossed and point at each other's receipts. | Spec 11.5; `vectors/ledger/matching-ledgers.json`; demo step 6; `verify-ledger.test.ts` (`npm run verify-ledger` checks two exports offline) | Ledgers are exported per person; the signed export format (spec 11.7) isn't built. |
| ALP can't control what a vendor's agent does with what it reads, or how a vendor stores it. | Spec 1.4, 1.5, 14 | **Limit**, stated as such. |

## One person's own agents

| Claim | Evidence | Limit |
|---|---|---|
| One person's agents write to each other through the home broker, which knows each agent's attestation and class from the organization's list, never from the agent. | Spec 5.4, 6.14; `core/own-agents.test.ts`; demo step 0 | |
| Each message reaches the receiving agent under a line the broker writes, naming the sending agent and its class, such as "from your own agent muse (consumer, self-attested)". | Spec 6.14 item 5, 12.1.6; `mcp/thread.test.ts`; demo step 0d | What the receiving agent does with the line is up to it; the broker's checks don't depend on it. |
| A confidential field reaches company agents that sign in with a credential only the company holds; the personal agent gets the message without it until the person decides on their approvals page. | Spec 6.14; `core/own-agents.test.ts`; demo steps 0a and 0b | See the row "The broker can tell a person's company agent from their personal one" for which agents can present such a credential. |
| A lower class or attestation in the organization's list applies at once to agents already connected; a higher one at the agent's next sign-in. | Spec 5.4; `core/review-hardening.test.ts` | |
| A personal access token is never recorded above `self` and `business`, so it can never pass for an enterprise agent. | Spec 5.7; `core/review-hardening.test.ts` | |
| An agent never reads a message its person's rules kept from it, in the inbox, the thread view or acknowledgements. | Spec 5.4, 6.11, 12.1.4; `vectors/delivery/visibility.json`; `core/review-hardening.test.ts`; `mcp/thread.test.ts`; `core/own-agents.test.ts` (an agent given a disconnected agent's name reads nothing addressed to or sent by the earlier one), `web/web.test.ts` and `oauth/oauth.test.ts` (the same through a personal access token and a dynamically registered client) | |
| Several of one person's agents may each answer the same request addressed to that person. | Spec 12.1.4; `vectors/delivery/visibility.json` (an agent reads what is addressed to its person, and nothing addressed to another of the person's agents) | **Limit**, stated as such. To limit who answers, the sender names one agent with `to_delegate`, or the organization gives the scope to one client in its `clients` list, in `enforce` mode: the person's agents on other clients can still read the request, but can't send in that scope (spec 6.6 step S2, 6.10). Products that share one connection, such as Claude and Claude Duet, are one agent to the broker, so either may answer what reaches it. |
| The broker can tell a person's company agent from their personal one. | Spec 5.4 (`org-client`, `tenant`); demo steps 0 and 0e | **Limit:** only for a client that authenticates at the token endpoint with a credential only the company deployment holds. For a public client the split guards against mistakes, not against the person. Whether ChatGPT or a company Claude can present such a credential through a custom connector is unverified; Anthropic's organization sign-in assertion (Claude-issued) is in beta and the reference doesn't verify it. |

## How it works

| Claim | Evidence | Limit |
|---|---|---|
| Addresses look like email, and each domain that federates publishes which broker is home for its people. | Spec 4.1, 4.2, 4.5; `vectors/domain/resolution.json` | |
| Inside one organization, one broker serves everyone and needs no published domain document. | Spec 3.3 (the Local profile); `core/broker.test.ts` (Act 1 runs with no domain document) | |
| An organization can run its broker on its own servers or inside its workspace platform, start with its own people and no public domain document, and federate when ready. | Spec 3.3 (the Local profile is the default starting point, needs no domain document, and can live inside the organization's own workspace surface); `SELF-HOST.md` | **Limit:** an approvals interface for workspace surfaces is future work (spec 19): approvals happen on the broker's own page. |
| Across organizations, brokers federate the way mail servers do. | Spec 12.2; demo steps 1 to 6; `npm run demo:federation` | Federation is Experimental in v0.1. |
| Client mode works through one custom connector, with no vendor work. | Spec 3.4, 12.1; `mcp/binding.test.ts` (the MCP SDKs' own clients, both protocol eras); bridge kit; the test with real agents (next section) | **Limit:** per-product rules apply (next section); real vendor agents: tested together on November 7, 2026, on a development broker with test identities (Claude and Claude Duet through a custom connector with OAuth, Muse through the REST mirror with a personal access token), and Claude on claude.ai again on November 8, 2026, through Entra sign-in ([SELF-HOST.md](SELF-HOST.md#tested-against-a-live-entra-tenant)); ChatGPT and dots, Grok, Gemini and Microsoft 365 Copilot not yet. |
| An A2A agent can join the same way. | Spec 12.4 (an A2A agent can be a delegate: its person connects it to their home broker through the client binding) | **Limit:** no A2A agent has been tested; an A2A mapping between brokers is future work (spec 12.4, 19). |
| The agent gets seven tools. | Spec 12.1.2; `schemas/client/tools.json` | |
| Threads are conversations: either agent can answer, ask a follow-up question, ask back or add an update in the same thread, until one side closes it or it expires. Each message is checked by both brokers and recorded in both ledgers, like the first. | Spec 7.8, 9.1 to 9.4; `vectors/threads/conversations.json`; `vectors/policy/sender.json` and `recipient.json` (a turn the relationship's terms allow in its direction is accepted, one they don't is refused); `core/threads.test.ts`, `core/conversations.test.ts` (between one person's agents, and between two people across two brokers, with both ledgers), `core/conversation-rules.test.ts` (both brokers enforce the availability window, the accept rule, the end of agreed terms and the thread limit); `mcp/thread.test.ts` (paging a long thread, replies that stay with the agent being answered); demo step 5 | A thread grants nothing: each message needs the relationship's terms for its own direction, so where an organization's default goes one way only, the other side can answer but not ask back, and an availability answer keeps to the window its recipient asked about. In a negotiation, only the negotiation types apply until the commit. A thread takes at most 200 messages; a longer conversation continues in a new thread. |
| A refusal's code says whether to fix the draft and send it once more, tell the person, or wait (for `not_disclosed`, its message says which); its message says what was wrong and what to do, without repeating any value the agent submitted (fields are named by pointer). | The error table in `schemas/client/openapi.json` and `bridge-kit/agent-instructions.md` sort the codes of spec 18.3 into those three kinds; `mcp/refusals.test.ts` (each kind of message; no submitted value in the message or the refusal's ledger entry; a draft with thousands of refused fields answered in bounded time, with a ledger entry of bounded size); `mcp/delivery-refusals.test.ts` (`retry_after` when the recipient's broker refuses, `unreachable`, a new `idempotency_key` for a corrected draft); `mcp/rest.test.ts` (the same advice on the REST mirror, `Retry-After`); `core/rate-limits.test.ts` (`retry_after`) | **Limit:** what is wrong with each field is in the message text only; there is no machine-readable detail per field yet. Spec 18.3 gives each code a status and whether it is retryable, not one of the three kinds. |
| For an agent that a command or an API call starts, a small script can check the inbox and start the agent only when something new has arrived. | `bridge-kit/poller/alp-watch.mjs`; `poller.test.ts` (a quiet check wakes nothing; a new message wakes the agent once, with its id only) | **Limit:** it can't start a hosted agent product such as Claude or Muse, whose documentation describes no push for custom connectors (SOURCES, read November 6, 2026; push is documented only for ChatGPT and Grok Bot, in the row on push below), so those keep their scheduled checks. It needs a read-only personal access token for the agent's name. For an agent connected through OAuth, whose name the broker's page won't give a token, a poller with its own name doesn't see messages addressed to that agent with `to_delegate`. |
| Native mode: a provider builds the client side into its agent. | Spec 3.4, 13.6 (Experimental) | **Limit:** no Native Client exists yet, and in v0.1 approvals still happen on the approvals page. |
| A provider can also run its own broker for addresses on its own domain. | Spec 13.7 (Provider Broker, Experimental) | **Limit:** no provider broker exists yet. A provider would need its own implementation: making the reference broker available to its users as their broker, in a commercial product or service, is a Competing Use under the reference broker's license (`reference/LICENSE.md`). |
| When a provider adopts, people keep their addresses and relationships. | Spec 3.4 | Moving between home brokers needs an export format that is future work (spec 19). |
| The reference broker runs on Node 22.18 or later, with a file or Postgres store. | `SELF-HOST.md` (including "Evaluate on one machine", run end to end on November 8, 2026); `storage/store.test.ts`, `storage/binding-store.test.ts`; `main.test.ts` (`npm start`'s checks before it listens) | **Limit:** the approvals page runs on loopback (test sign-ins or single sign-on), or on the broker's public origin behind invites and passkeys; single sign-on on the public origin isn't built. The Postgres code runs on PGlite (Postgres compiled to WebAssembly) in `npm test`; the whole suite also passed against a PostgreSQL 17.10 server with `ALP_TEST_POSTGRES_URL` on November 8, 2026, and `.github/workflows/ci.yml` runs it on Postgres 17. It hasn't run against a hosted database (Supabase) yet. |
| The broker can sign people in through their organization's OpenID provider, such as Microsoft Entra ID, binding each person to the provider's issuer and subject (for Entra the tenant and object id), with app roles or groups as policy groups and a re-check at the provider at every token refresh. | Spec 5.2, 5.3; `SELF-HOST.md`; `oauth/oidc.test.ts`, run against a standard OpenID provider in the test process: the full code flow with PKCE, state and nonce; a wrong issuer, wrong audience, bad nonce, expired token and wrong tenant, each refused; an address change keeping the principal_id and a recycled address getting a new one; groups mapping and the groups overage refused; a disabled account's connection ended at refresh; the binding surviving a restart; a test against a live Microsoft Entra tenant on November 8, 2026, with test users ([SELF-HOST.md](SELF-HOST.md#tested-against-a-live-entra-tenant)): sign-in, the `tid` + `oid` binding, app roles as policy groups, and the re-check at every token refresh, which ended a disabled user's connection | **Limit:** built and tested against a standard OIDC provider, and once against a live Entra tenant with test users, with app roles only: no Conditional Access policy, group claims or groups overage, guests or multi-tenant app tried there yet. Personal access tokens and open web view sessions aren't re-checked at refresh, and SCIM isn't built. The demo and `npm run dev` use test identities. |
