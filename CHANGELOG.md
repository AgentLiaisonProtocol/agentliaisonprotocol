# Changelog

All notable changes to the Agent Liaison Protocol (ALP) specification, schemas and vectors are recorded here. The specification uses semantic versioning; while the major version is 0, any release may change things incompatibly.

## [0.1.1] - Unreleased

A patch: the protocol version (`"alp": "0.1"`), the schemas and the vectors don't change.

### Fixed

- Reference broker, `alp_whoami` (spec 6.14, 12.1.2): `scopes` in the structured result, which is all the REST mirror returns, now lists every scope the agent can use. Before, it listed only what the person's relationships allow; the scopes the agent may use with the person's other agents, and with `include_scopes` their body schemas, were only in the MCP text. A REST client, or an MCP client that reads only `structuredContent`, whose person had no relationships got `"scopes": []`: it couldn't learn the fields for writing to the person's other agents, and a send to them with wrong fields was refused with `schema_invalid`, whose advice ("alp_whoami with include_scopes returns the schemas") it couldn't follow. Now `scopes` also lists, while the person has another agent that can receive a message, what the agent may send the person's other agents (the types that start a thread and those an open one takes), merged per scope with what relationships allow: one entry per scope, sorted by id, with the types of both and, with `include_scopes`, a body schema for each type. It lists at most 64, as `tools.json` allows; past that, what relationships allow is kept first, so connecting another agent never pushes out a scope that 0.1.0 listed. In `enforce` mode, the organization's list of agents limits both, as before. `schemas/client/tools.json` and `schemas/client/openapi.json` don't change, so the result still validates against a client's 0.1 tool snapshot; the tool's description already said "the scopes you can use". [KNOWN-GAPS.md](KNOWN-GAPS.md) keeps what is left: structured results don't name the person's other agents or say which listed types work with them; either would change the output schema.
- Reference broker, `alp_whoami` text: it still says which scopes work with other people and which with the person's own agents; when the person has other agents, the first list reads "Scopes you can use with other people". With `include_scopes`, it says that every body schema is in `structuredContent.scopes[].schemas`, and still carries the schemas for writing to the person's other agents, for platforms that show only text.
- Specification 12.1.2: the usable `scopes` of `alp_whoami` are those the delegate may use with other people under its principal's relationships, and those it may use with its principal's other agents (Section 6.14); a scope usable both ways is listed once, with the types of both. This says what the table and the tool's description meant; no schema changes.
- Reference broker, authorization server (spec 4.3): every fetch of a client ID metadata document or a client's key set, its body included, ends within 2.5 seconds. Before, one stalled fetch could make a client's sign-ins, and its token refreshes once oidc-provider's cache of its document had expired, wait forever, until the broker restarted, while other clients still signed in. oidc-provider makes every authorization of a client wait on the first fetch of its metadata document (and its token requests on the first fetch of its key set) and relies on a 2.5-second abort signal to end that fetch, but Node's fetch can leave a compressed response body pending forever when the signal fires after the body's last bytes arrived and before they were decoded (a document served chunked and compressed, on a busy machine). The broker now settles each fetch by that deadline whatever Node's fetch does, asks for an uncompressed body (`Accept-Encoding: identity`), and cancels at once the body of a metadata document's answer other than 200, which oidc-provider never reads, so a server that keeps sending can't hold the connection open. A metadata document whose fetch failed or ran out of time is fetched again only after the failure wait that already applied (120 seconds).

### Changed

- Bridge kit (the Grok guide, its sources and the bridge-kit README) and CLAIMS.md: Grok's provider is named SpaceXSI (formerly xAI), as its documentation and consumer terms now say, and the Grok guide states what the consumer terms of October 27, 2026 say about agent actions. What the Acceptable Use Policy says about automated use stays unverified.

## [0.1.0] - 2026-11-09 (draft for implementers)

First public draft.

### Added

- The specification ([spec/alp-v0.1.md](spec/alp-v0.1.md)), with maturity labels on every section:
  - addresses on domains, one home broker per principal, and domain documents at `/.well-known/alp.json` with key pinning, monotonic serials and bounded caching;
  - the Local profile, in which one organization's broker serves its own people with nothing published;
  - identity bound to an immutable `principal_id`, delegates with attestation (`self`, `vendor`, `native`, `org-client`, `tenant`) and class, and the OAuth 2.1 profile of the client binding (client ID metadata documents, PKCE S256, issuer identification, audience-bound tokens of at most 15 minutes, rotating refresh tokens) plus personal access tokens;
  - connection requests that reach people, grants, private organization policy, and the sender-side and recipient-side evaluation algorithms;
  - messages between one person's own agents, with the organization's delivery minimums applied per field and per receiving agent (Section 6.14);
  - five core scopes: `alp.availability/1`, `alp.meeting/1`, `alp.briefing/1`, `alp.status/1` and `alp.document_request/1`;
  - envelopes signed with detached JWS over JCS, with explicit `typ` values and `aud`;
  - threads that carry a conversation between two people's agents, two-person ratification records and commits;
  - delivery with receipts, digest-chained ledgers that cross-reference each other, and an OCSF-mapped security event stream;
  - the MCP client binding with a fixed tool list and a REST mirror, the federation binding (Experimental), push adapters (Experimental), A2A notes, and the web view with notifications that only notify;
  - conformance classes with requirement ids, security and privacy considerations, registries and future work.
- JSON Schemas (2020-12) for every object, the five core scopes, the tool list and an OpenAPI 3.1 document for the REST mirror.
- Conformance vectors with TEST-ONLY keys, and the specification tools that generate and check them.
- The reference broker ([reference/](reference/)): the core, the MCP and REST client binding with an OAuth 2.1 authorization server, sign-in through an organization's OpenID provider (generic, or Microsoft Entra ID), the person's web view, the federation binding, file and Postgres stores, `npm run demo` over real HTTP (opening with one person's three agents of different trust), and a test suite that runs every conformance vector. That sign-in is built and tested against a standard OIDC provider, and was tested once, on November 8, 2026, against a single-tenant Microsoft Entra ID (Free) tenant with test users (sign-in, the tenant and object id binding, app roles in policy, a fresh sign-in for each approval, and the re-check at each token refresh, which ended the agent connection of a user whose account was disabled; [SELF-HOST.md](SELF-HOST.md#tested-against-a-live-entra-tenant)). See [reference/ARCHITECTURE.md](reference/ARCHITECTURE.md).
- The bridge kit ([bridge-kit/](bridge-kit/)): a generic client-mode guide, guides for Claude, ChatGPT and dots, Microsoft 365 Copilot, Grok, Gemini and Muse, the agent instruction snippet, and what a test with real agents (Claude, Claude Duet and Muse) showed on November 7, 2026.
- [SELF-HOST.md](SELF-HOST.md) and a Dockerfile for running a broker.

### Added (reference broker): the parts a hosted broker needs (see SELF-HOST.md)

- With `DATABASE_URL`, the client binding's state (the authorization server's grants, sessions, codes, refresh tokens and registrations, personal access tokens, held connection requests, send idempotency) and the rate and replay windows of sign-in, registration and the web view live in Postgres, so several instances given the same `ALP_OAUTH_KEYS` can serve one broker (migrations 002 and 003). The federation inbox's per-address limit and request-signature nonces stay per instance. Unused dynamic registrations expire after 30 days.
- No usable token is stored: refresh tokens, authorization codes and session cookies are kept only under the SHA-256 of their value (oidc-provider's copy of each id is left out of the stored payload; migration 005 and the file store clean older state). A revocation of an invite or a personal access token can't be undone by a sign-in or request already in progress, and only one first passkey is stored even when two registrations land at once. Postgres allows one live principal per address and per identity (migration 006).
- The person's web view on the broker's public origin (`ALP_WEB_PUBLIC=1`, off by default): sign-in by invite (`npm run invite`; one secret per person, with expiry and revocation; it needs `DATABASE_URL` and the public web view), a passkey registered before anything else and checked at every later sign-in, a fresh passkey assertion with user verification for every approval, ratification, grant change and token whose challenge carries the hash of the terms (spec 12.5.2), `__Host-` cookies, Origin checks, a stricter CSP, a notice on sign-in from a new browser, and request limits. The agents' sign-in page asks for the passkey too.
- Limits strangers can't use up for everyone: OIDC sign-ins started on the public connector page count per source (an IPv6 /64 as one), apart from the web view's sign-ins and approval step-ups; the connector sign-in page takes at most 120 requests a minute per source before it checks any secret; invite secrets are checked with scrypt off the event loop.
- Keys held outside the database: `ALP_OAUTH_KEYS` and `ALP_KEYRING_KEY` (`npm run hosted-keys -- ./hosted-secrets.json`), which seals the signing keys stored in Postgres. Row-level security with no policy on every table (migration 004). `npm start` reads `ALP_ACCESS_TOKEN_TTL` (60 to 900 seconds), as `npm run dev` does.
- The Postgres suites run in `npm test` on PGlite (Postgres compiled to WebAssembly, in the test process).
- `npm start` refuses a policy whose `dlp.hook` names an outside DLP service: it connects none, and the sample check would otherwise run in its place unannounced.
- `reference/deploy/VERCEL-SUPABASE.md` (deployment note) and `reference/deploy/OPERATOR-STATEMENT.md` (the operator statement of spec 13.9, as a template).

### Changed before publication

The test with real agents on November 7, 2026 ([bridge-kit/README.md](bridge-kit/README.md#tested-with-real-agents)) ran the reference broker without these changes.

- Specification 2, 6.3, 6.4, 6.6, 6.7, 6.12, 7.2, 7.6, 7.8, 8.2, 9, 12.1, 13.3 (BC-16), 14, 15 and Appendix B, the core scopes, the client binding's tools, the vectors, the independent validator, the bridge kit and the reference broker: threads are conversations. Before, a thread was effectively one exchange: the scopes' `replies` maps let an `inform` be answered only by an `ack` (and `ask_human`, or a `request` in `alp.status/1`), so an agent couldn't answer an update with its own, or ask a follow-up question after an answer, in the same thread, and had to start another.
  - Replies: in `alp.availability/1`, `alp.briefing/1` and `alp.status/1`, a `request` may be answered by `inform`, `request`, `decline`, `ack`, `ask_human` or `error`, and an `inform` by `inform`, `request`, `ack`, `ask_human` or `error`. In `alp.meeting/1` and `alp.document_request/1`, a `request` may also be answered by a `request` before anyone proposes, and an `inform` by an `inform` after the commit. A reply names an earlier message of the thread, from either side, except that an `accept` or a `counter` answers the other party's latest proposal; a message that names none follows up: a `request`, an `inform`, an `ask_human` or an `error`, or a type that may start the scope's threads.
  - States (spec 9.2): `open` takes requests and informs in both directions; `negotiating` and `agreed` take only the negotiation types, so nothing said around a negotiation can change agreed terms or stand in for an `accept` or a `commit`; in a negotiable scope an `inform` reports what happened after the commit, and only `committed` takes it. The reference now refuses what the state table doesn't list. Before, it accepted a `request` or an `inform` in any state that wasn't closed; a new `propose` in `negotiating` (as a follow-up in `alp.meeting/1`, or answering a request in either negotiable scope) or in `agreed`, which replaced the terms on the table or voided the agreed ones; a `counter` in `agreed`, which voided the agreed terms; a `decline` after a commit; and an `accept` or a `counter` of the sender's own proposal, or of one a later proposal had replaced. One person's own agents, who never negotiate, can no longer send an `inform` in a `alp.meeting/1` or `alp.document_request/1` thread.
  - How a thread ends: an `ack` with status `completed` from either side, except in `agreed`, where an `ack` only acknowledges and one with status `completed` is refused; a `decline` of the thread's first message, of a proposal or of the agreed terms (`cancelled` once terms are agreed), while a `decline` of a later question turns down that question only; or expiry. Each message moves the thread's expiry to its own when that is later, except that in `negotiating` and `agreed` only a `propose`, `counter` or `accept` does, so acknowledgements and errors can't keep terms waiting. A committed thread doesn't expire. A thread takes at most 200 messages besides one that ends it; then the participants continue in a new thread.
  - Ratification (spec 9.4): a `commit` needs both ratification records unexpired when it is sent and when it is received; before, a commit was accepted on records that had expired weeks earlier. When a thread leaves `agreed` without a commit, each broker voids its person's pending ratification requests for it, and a request approved after that says the thread was closed, not that the terms changed. The reference's side that receives an `accept` now ratifies (by standing grant, or by asking the person) once its answer is out: before, a standing grant on that side sent its ratification ack before the accepting broker had recorded its own accept, the ack was refused, and every later commit failed with `needs_ratification`. A reply to a message the recipient's broker doesn't hold yet is refused `thread_state` with `Retry-After`, as spec 9.3 says, so the sender's broker retries it.
  - Availability (spec 7.8): every free interval in an `alp.availability/1` `inform` lies inside the window of the request the inform answers, when its recipient sent it, or otherwise of the latest request its recipient sent in the thread; an `inform` that answers its own sender's request, or whose recipient asked nothing, is refused. Before, only an `inform` answering a request was checked, against whichever request it named, so an update, a follow-up or an answer to the sender's own question could carry intervals nobody asked for. Both brokers check it, from their own copies of the thread.
  - `may` (spec 6.6, 6.7): `ack`, `decline` and `error` need no `may` at either broker, so either side can always acknowledge, close a thread or turn something down; `ask_human` still does. Before, the specification and the independent validator required `may` for them while the reference didn't.
  - Every message in a thread is still a full message: both brokers evaluate it (the relationship's `may` for its own direction, field coverage, the organization's rules, DLP, rate limits), both ledgers record it, and it is delivered in the untrusted-content wrapper.
  - Client binding: `alp_thread` takes `limit` (default 50) and `before`, returns the latest messages the agent may read with `earlier` (how many come before them) and `counterparty.agents` (the other side's agents in the thread, newest first), and its text covers that page only. Before, the reference read a thread's oldest 1,000 records and showed up to 500 of them, so in a long thread the newest messages, and the `next_types` that answer them, were missing; it now reads newest first (`MessageQuery.order` and `before` in both stores). `next_types` comes from the whole thread, offers `accept` and `counter` only while the latest proposal is the other side's, `commit` only while both ratifications are valid and to a side that may commit, and, in a thread that holds 200 messages, only what ends it; the text then says to continue in a new thread. A reply that names no `to_delegate` goes to the agent that sent the message it answers, so a conversation stays with the agent that holds it; `alp_thread`, `alp_inbox`, the MCP server's instructions and the bridge kit's snippet tell agents to give a follow-up the `to_delegate` of the agent they are talking with, and how to close a thread (`alp_send` an `ack` with status `completed`, which isn't `alp_ack`). A held reply or follow-up says, to the agent, in the person's notification and on their page, by when the person must approve it when its thread would expire first. The tool descriptions in `schemas/client/tools.json` and the OpenAPI mirror say the same.
  - Policies: the development broker pre-approves `alp.status/1` between staff in both directions. The example policy's briefing default goes both ways, so the side that answers can also ask back.
  - Vectors: `vectors/threads/conversations.json` (16 threads, turn by turn, including the availability window, the thread limit, the accept and counter rule and how agreed terms end), and cases in `vectors/policy/sender.json` and `vectors/policy/recipient.json`: a reply asking a further question in the relationship's direction is allowed, a question back against it is refused, and an `ack` or a `decline` that the relationship's `may` doesn't list is allowed. The independent validator evaluates the conversation vectors with a state machine of its own.

- Reference broker, hold for review (spec 6.12): approving a held message that opens a thread sends it in the thread id `alp_send` returned when it held the message. Before, the broker refused the release (`thread_state`, "unknown thread") while the person's page still said the message was sent. A held message now keeps the outcome of its release: `sent`, or `refused` with the code sending answered. The page says only what the broker knows: "Sent", "Refused by the recipient's broker", "Delivery failed" (the message may still have arrived), or "Not sent" when the broker itself didn't send it. Approving writes a `released` ledger entry, as discarding already did; the record and that entry name an envelope id only when the broker signed the envelope.
- Reference broker, hold for review: a held message leaves `pending` in one atomic step, through a new store method (`claimHeldOutbound`; a conditional update in Postgres). Of two decisions at once (a double submit, two tabs), one acts and the other is refused; before, both could send it. While it is being sent the record is `sending`. An approval that fails on the way (a store or connection error) ends it with what sending answered when only recording that failed (`sent`, or `refused` with the code), with its `released` entry, which is written once even when a write landed but reported a failure; otherwise it puts it back to `pending` if nothing was signed yet, and ends it `refused` (`undeliverable`, `internal`) if something was, since the message may have arrived. Only a broker that stops before recording the outcome leaves it `sending`, so it is never sent twice, and the page says so and points to the ledger.
- Reference broker, one person's own agents (spec 6.14): when the whole message waits for the person, the held record names the withheld fields and their labels (`whole`), and the notification names the labels and what the receiving agent would need (never values). The person's page tells a held message whose rest already went to the agent (the record keeps that copy's envelope id) from one of which nothing was sent, before and after the person decides: a discarded or expired message whose rest went says so, never "nothing was sent". A record written before these fields that names withheld fields is shown as one whose rest went (its copy's id wasn't kept). The page names the agent that wrote the message and the one it is for, and gives each reason its own text (the person's rules, a data-loss check, the organization's minimums; for messages to the person, quiet hours or delivery constraints).
- Reference broker, connector sign-in (spec 5.4, 5.6 item 5): the consent page tells a client the operator pre-registered from a dynamically registered one: it shows the registered name, without "(unverified name)", no longer calls it dynamic registration, and says why it is recorded as `self`. It shows nothing from any organization's list of agents (the person isn't known before they sign in, and organization policy is private). Before, for a client another organization on the same broker lists, it showed that organization's attestation and name, and for a dynamically registered one asked for no name, though neither applied to the person. It now shows the attestation and the name the client itself gives (a metadata document's host, the operator's registration), says that the person's organization's list may change them, and asks for a name for any dynamically registered client. Such a client, when it connects for the first time, gets a label made from its registered `client_name` (lower case, hyphens for other characters, at most 32 characters, `-2` and so on when the label is taken, `agent` when it has none) instead of a name the person types. A person who connected it before keeps the label they have.
- Specification 6.7, 8.2, 12.1.3 and 12.2.4, and the reference broker: a message whose `to.delegate` names no delegate of the recipient that may receive it (none with that label is active, it is blocked, or its client is refused) is accepted and held for the person's web view, with a notification that leaves out the label. It never goes to the person's other agents. Before, the reference stored it as delivered, where no agent could read it and the person wasn't told.
  - Answering the sender: the receipt is the same, and so are the store writes the recipient's broker makes before it answers. The hold is recorded in the `received` ledger entry written either way (`ref`: `web_view`, or `until:` and the end of quiet hours; spec 11.2; the person's ledger page shows it), whose salt keeps the receipt's `ledger_hash` from revealing it (below), so a broker that stops right after answering loses only the notice.
  - After the answer: what a hold adds (the person's notification) and the pushes to agents run after the answer, through a `background` hook in the broker's options (by default the next turn of the event loop; between two principals of one broker, after the sender's whole call has returned, the client binding's idempotency record included). When `npm start` or `npm run dev` stops (SIGINT, SIGTERM), it waits up to 10 seconds for that work before it closes its stores and exits.
  - Notifications: messages held because of the person's agents (a `to.delegate` none can receive, or constraints none meets) get at most one notification an hour per sender, which spec 6.7 now allows for both reasons (a broker MAY digest or limit them, except for `ask_human`); the page lists them all. An `ask_human` tells the person each time that an agent asks for a decision, whatever it waits for, outside the grant's quiet hours.
  - Quiet hours: during them the person is told of nothing from that sender, whatever the message waits for (the page lists it), as spec 6.7 now recommends: notifying only of the messages held because of the person's agents would let the sender disturb the person at night and learn from their response that a message waits for them. When they end, the person is told what they would have been told had each message arrived then, as spec 6.7 now says: the broker keeps each such notification in its store (Postgres migration `007_deferred_notices.sql`) and `sendDueNotices`, which `npm start` and `npm run dev` run every minute, sends the due ones.
  - Acceptance step 0 (spec 12.2.4) now also refuses an envelope whose `from.delegate` or `to.delegate` isn't a delegate id of `from.address` or `to.address` (`bad_envelope`); the reference already did so for `from.delegate`.
  - Vectors: `vectors/federation/acceptance.json` gains three cases, and `vectors/policy/recipient.json` five that name one of the recipient's agents in `to.delegate` (Lee has three more agents in `world.json`: one on a consumer client, one blocked, one whose client the list doesn't name); the independent validator now counts only the agent named, and only agents that aren't blocked and whose client the list allows.
- Specification 5.4 and 12.1.4, and the reference broker: any binding with an agent's label other than the same client signing in again for the same person while its binding is active is a new binding: one that takes the label of an agent the person disconnected, and one given an active agent's label through `registerDelegate` by another client. Before, a token minted with a disconnected agent's name read that agent's messages, including fields cleared only for the earlier agent's higher class.
  - Reads: it reads nothing addressed to, or sent by, the earlier one (inbox, thread view, acknowledgements): a received message counts from when its broker received it, a sent one from when its broker signed it. Acknowledgements are per binding too: what the earlier agent marked handled is unread for the new one. Messages addressed to the person stay readable, as for any newly connected agent. The stores leave an earlier binding's messages out of the inbox query (`bindingSince`), and a page of only records an agent may not see says there is more, with a cursor past them.
  - Sends: it doesn't get the earlier one's `alp_send` results for an idempotency key, and a held message is sent only as the agent that wrote it and, between the person's own agents, only to the agent it was written for; otherwise the page offers only to discard it.
  - Tokens and connections: personal access tokens record their binding, and connections the binding they were authorized for: neither acts for a later agent, even when the earlier one was disconnected some other way than the web view and the same client connected again under its name. A connection authorized before this change is bound the next time it gets a token, or ended if the agent it would act for started after it was authorized (see the upgrade note). The token page says when a name starts a new agent, and when a token is added next to one that still works.
  - Vectors: `vectors/delivery/visibility.json` gains three cases (the reader's `since`, a sent message's `created_at` and a received message's `stored_at`).
- Reference broker, upgrade note: `alp_send`'s idempotency keys now include the binding's start, so a key stored before this change no longer matches: a send retried with the same key within 24 hours of the upgrade is sent again.
- Reference broker, upgrade note: a connection (an OAuth grant) authorized before connections recorded their binding acts, as before, for the client's newest active agent until it next gets a token, usually its next refresh; that token binds it to that agent, and from then on it stops once the agent is disconnected. If that agent started after the connection was authorized (the agent it was for was disconnected some other way than the web view, and the same client connected again under the name), the connection stops instead: its refresh is refused, the connection is revoked, and the client must connect again. Until its next token, disconnecting the agent on the web view ends it, as it ends any connection of the agent's.
- Specification 6.7, 11.2, 11.4, 13.3 (BC-19) and 14, `schemas/ledger-entry.schema.json`, the vectors, the independent validator and the reference broker: every ledger entry carries a `salt`: 16 to 64 random bytes (at least 128 bits) as unpadded base64url. A receipt gives the sender the hash of the recipient's entry, and the sender knows or can guess every other member of it, so it could confirm a guess of what the entry records: whether the message waits for the person, or whether anything was written between two of its messages. `vectors/ledger/matching-ledgers.json` and the worked examples carry salts, so their hashes and the receipt's signature changed. Upgrade note: entries the reference wrote before have no salt; they still verify, but don't validate against the schema, which now requires it.
- Specification 10.3 and 18.3: `alp_send`'s idempotency is per delegate binding (Section 5.4), and `unknown_recipient` also covers a `to_delegate` that names no active agent between one person's own agents (Section 6.14), as those sections already said.
- Specification 5.4: attestation `self` also covers a client the broker's operator pre-registered that the organization's `clients` list doesn't name, which the reference already recorded as `self`.
- Specification 12.1.3 and the reference broker's `alp_send` text: `delivered` means the recipient's home broker accepted the envelope, not that an agent read it or can. To another person the text now says "Accepted by lee@example.org's broker", names the agent `to_delegate` addressed and any delivery constraints the sender's own organization added, and says their broker passes it on or holds it without saying which; it is built only from the sender's side, so it reads the same whatever happened at the recipient's. Between one person's own agents it says "Delivered to your agent muse", or that the agent can't receive messages now and the message waits for the person; a message held whole for the person names the labels and the agent. The structured result doesn't change. The bridge kit's instructions ask agents to report a send as accepted by the other person's broker.
- Reference broker, `alp_whoami` text (spec 6.14): it names the person's other agents that can receive a message now, with the class and attestation the broker ranks them at ("Your person's other agents: muse (consumer, self-attested)"), or says there are none; says how to write to them (`to` = the person's own address, `to_delegate` = the agent's label, no connection needed); and lists the scopes the agent's client may use with them, each with the types that start a thread and those that continue one. With `include_scopes`, the text also carries those types' body schemas. A person with other agents but no relationships is no longer told "You have no relationships yet", which could lead an agent to conclude it could send nothing, and an agent whose client may use none of the scopes of the person's relationships is told that instead of that there are none. Only the same person's agents are named. The structured result doesn't change: its `scopes` still lists only what the person's relationships allow.
- Specification 12.1.4: a scope given to one client in the `clients` list keeps the person's agents on other clients from answering in it only in `enforce` mode, and they can still read the request, as Sections 6.6 (step S2) and 6.10 already said. A sender that wants one agent's answer can name it in `to_delegate`.
- Reference broker, connection requests (spec 6.2, 9.4): the terms a person seals by approving a connection request without choosing terms (the scope's suggested fields) now include `commit`, with `commit: ask_me`. Before, they left it out, so a meeting or document request set up that way reached `agreed` and every commit was refused with `type_not_allowed`. A commit still needs both people's ratification records, and grants never leave their broker, so nothing changes on the wire. Both consent pages of the web view say what a commit takes, and `alp_thread`'s `next_types` offers `commit` once both records are held and, in `alp.document_request/1`, only to the side whose proposal was accepted.
- Reference broker, refusals (spec 18.3): each schema problem is described from the schema (the allowed values, the expected type, the date-time form, the bound, the missing field, the fields allowed where an unknown one was found), and the message joins every reason within 1,000 characters. A `not_disclosed` field that the scope doesn't define says so, with the fields it does define, the closest one and the draft's other schema problems; an unnamed free-text field, `org_policy` (the organization's rule id), `type_not_allowed`, `federation_blocked`, `body_too_large` and `dlp_blocked` each get their own text. Codes and pointers are unchanged, and no reason carries a submitted value. What one refused draft costs doesn't grow with the square of its refused fields: each reason's text is bounded (a pointer is shown by its first 120 characters, a list of pointers by about 300, then "and N more"), the message stops collecting once it is full, the error lists only pointers `tools.json` allows (at most 512 characters), and the `refused_outbound` and `refused_inbound` ledger entries keep the first 64 reasons and count the rest.
- Reference broker, redaction (spec 6.6, 8.2): a draft with more leaves to remove than `decision.redacted` can list (64 pointers of at most 512 characters, `common.schema.json`), under redaction `redact` or an organization's `redact` rule, is refused as without redaction (`not_disclosed`, or `org_policy` naming the rule) before anything is signed. Before, the broker signed an envelope no broker accepts (`bad_envelope`) and its `sent` ledger entry listed every removed pointer: for a 30,000-character member name above 3,500 fields, 105 MB, after about 18 seconds. Such a draft is now refused within the bounds of any other refusal.
- Reference broker, `type_not_allowed` between one person's own agents (spec 6.14 item 2): the message says that propose, counter, accept and commit aren't sent between one person's own agents, and points to `alp_whoami`. Before, it spoke of the person's terms with their own address and pointed to `alp_contacts`, which doesn't list the person's own agents.
- Reference broker, REST mirror (spec 12.1.9): an error's `message` ends with the advice an MCP client gets in its text; a body that isn't JSON is told where it stops being JSON, and about curly quotes; a byte order mark before the JSON is dropped (Windows PowerShell 5.1 writes one), and JSON that isn't an object is refused with 400; any method but POST on a tool's path gets 405 with `Allow: POST`; a refused token keeps the code `identity_mismatch`, and its message says what to do (refresh, create a new personal access token, add the `send` scope, or ask the administrator). Between one person's own agents, `unknown_recipient` lists the person's other connected agents.
- Reference broker, rate limits: messages between one person's own agents have their own bucket per sending and receiving agent (default 600 an hour; `ALP_OWN_AGENT_RATE_LIMIT`), apart from the limit between two people (default 120 an hour per counterparty; `ALP_DEFAULT_RATE_LIMIT`); each variable takes a count of at most 100,000. Every `rate_limited` refusal on the client binding carries `retry_after`, and the REST mirror sends `Retry-After`; a `rate_limited` refusal by the recipient's broker, a signed receipt or a plain HTTP 429 from its federation inbox, gives the `Retry-After` it came with, or 30 seconds, the first retry interval of spec 10.2, without one. `Store.hitRateLimit` returns the wait. A refusal's message is the broker's words closed as a sentence, then the advice.
- Reference broker, refusal advice (spec 10.3, 18.3): for a draft to fix (`invalid_input`, `unknown_scope`, `unknown_type`, `schema_invalid`, `body_too_large`, `thread_state`, `unknown_recipient`, a `not_disclosed` field the scope doesn't define), the advice says to send the corrected draft with a new `idempotency_key`, since the same key returns the first answer for 24 hours; `needs_ratification` and `discovery_failed` say so too. `unreachable` says the message may still have arrived and to tell the person instead of sending it again, in the advice, the MCP server's instructions, the bridge kit and the OpenAPI document alike; before, some said to try again later and the bridge kit said nothing was delivered.
- Reference broker, `alp_send` with an `idempotency_key` (spec 10.3): the first call claims the key before it sends, in one atomic step of the binding store (`BindingStore.swapIdempotency`; a conditional write in Postgres). A call with the same key while the first is still being sent (an agent whose client gave up and retried) no longer sends the message a second time: it gets `internal` with `retry_after` 2, and the first call's answer once it has one.
- Specification 6.8: step 8's rate limit and thread checks report `rate_limited` and `thread_state`, as the table of Section 6.7 says; before, 6.8 said that steps 7, 8 and 10 all report `not_accepted`.
- Specification 10.3 and 13.8 (CD-6): an `alp_send` with an `idempotency_key` used within 24 hours never sends again: it returns the first call's result, or `internal` with `retry_after` while the first call is still running. A broker answers `internal` only when the message can't have arrived, so after `internal` a call with the same key is evaluated anew. A delegate reuses its key to retry a send that got no answer or `internal`, and uses a new one for a corrected draft or to send again after any other refusal. Before, 10.3 said every result was returned, `internal` included, and CD-6 said to reuse the key for any retry, while the bridge kit and the reference broker's refusals said to use a new key after a refusal.
- Reference broker, `alp_send` after the envelope left: when the recipient's broker answers only `internal` (it was still evaluating the envelope when the retries ran out, or failed itself), or the sender's broker fails after writing the `sent` entry, the agent is told `unreachable`: the message may still have arrived, tell the person. Before, it got `not delivered` or `internal`, and a retry with the same `idempotency_key`, as the advice for `internal` says, sent the message a second time. So `internal` now always means that the message can't have arrived.
- Reference broker, security events (spec 5.1, 11.8): a send whose `from` claims another principal emits `token_refused` (`identity_mismatch`, naming the caller's principal, delegate and client, never the claimed address). A refused bearer token is written once per reason and client per minute, and the rest of that minute as one event with `detail.count`. An event the sink or the schema refuses is counted, reported on stderr at most once a minute and on `/healthz`.
- Reference broker, per-source limits: of a list-valued client-address header such as `X-Forwarded-For`, the entry `ALP_TRUSTED_PROXY_HOPS` from the right is the client's (default 1, the right-most), so a client can't choose its own source; before, the left-most was taken. Client metadata documents of clients an installed policy lists are fetched outside the per-source and total budgets, and the metadata fetch and dynamic registration budgets and the failed sign-in limits (the connector page's and the public web view's) count an IPv6 /64 as one source. `npm start` warns when `HOST` is `0.0.0.0` with no client-address header set.
- Reference broker, `npm start`: `SIGHUP` reloads each policy file on its own (an unchanged file is skipped, a changed one without a higher serial or a malformed one keeps its previous policy, and the others load), so a kill switch in a later file applies; before, the reload stopped at the first unchanged file. `ALP_PID_FILE` writes the process id. It refuses an `id` that isn't https and an `ALP_DEV_LOGIN_SECRETS` value under 12 characters (instead of replacing it), and warns when a policy sets `retention.ledger_days` (not enforced) and when Postgres runs without `ALP_KEYRING_KEY`.
- Reference broker, operations: `/healthz` and `/readyz` on the public listener; request log lines with full ISO 8601 UTC timestamps; the listen addresses in the startup banner and a `stopped` line on exit; `ALP_SECURITY_EVENTS` takes `file` or `stdout`. The Dockerfile has a `HEALTHCHECK`, writes security events to standard output by default and carries OCI labels.
- Reference broker, sign-in through an organization's identity provider: provider sessions are sealed with the first cookie key in `ALP_OAUTH_KEYS` and opened with any listed one, and sealed again at each successful re-check, so the usual key rotation (new keys first, old ones kept) no longer ends every connection at its next refresh. A session that can't be opened is logged as such, not as a refusal by the provider.
- Reference broker, sign-in through an organization's identity provider (found while preparing the test against a live Microsoft Entra tenant on November 8, 2026, which ran with these changes; [SELF-HOST.md](SELF-HOST.md#tested-against-a-live-entra-tenant)): with `provider: "entra"`, the code exchange and each refresh name the configured scopes again, which Entra's v2.0 token endpoint may require (it has been reported to refuse a request without them, AADSTS900144, and a refresh returns an ID token only when `openid` is asked for). A signed one naming another person still ends it.
