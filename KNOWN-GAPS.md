# Known gaps in v0.1

As of 2026-11-08. These are known gaps in ALP v0.1 and its reference broker. They are listed so that implementers and operators can plan around them. They are candidates for later versions, and none has a delivery date. [reference/ARCHITECTURE.md](reference/ARCHITECTURE.md#not-built-yet-and-where-it-goes) lists the reference broker's gaps in more detail.

## Protocol and client binding

- **Push to agents.** Spec Section 12.3 (Experimental) defines push adapters, but the reference broker sends no push. Agents check `alp_inbox` on a schedule. For an agent that a command starts, [bridge-kit/poller/](bridge-kit/poller/) polls and starts it only when something new has arrived. A hosted agent product whose documentation describes no push for custom connectors, such as Claude or Muse ([bridge-kit/SOURCES.md](bridge-kit/SOURCES.md), read November 6, 2026), keeps its scheduled checks.
- **Machine-readable refusal details.** A refusal carries `code`, `message`, `pointers`, `rule`, `categories` and `retry_after`. What is wrong with each field is stated in `message` only. On the REST mirror, authentication failures use the body code `identity_mismatch`, and the `WWW-Authenticate` header carries the OAuth error.
- **A person's own agents in structured results.** `alp_whoami`'s `scopes` lists only what the person's relationships allow. The person's other agents are listed only in the MCP text result of `alp_whoami` and in the message of an `unknown_recipient` refusal; a structured result names one only as a message's sender, in a message's signed envelope with `include_envelope` (its `from` and `to`), or, in `alp_thread`'s `counterparty.agents`, as an agent that wrote in that thread. Inbox items don't show that another of the person's agents has already replied.
- **Polling for OAuth-connected agents.** No credential lets a polling script watch an agent connected through OAuth. Today the polling pattern needs a personal access token for the same agent name.
- **Stricter message rules.** These are not built yet: a single date-time spelling, time windows whose end must follow their start, refusing fields a scope doesn't define with `schema_invalid` (today they get `not_disclosed`), and example bodies inside scope definitions.

## Reference broker

- **The web view behind single sign-on.** Serving the person's web view on an HTTPS address behind the organization's single sign-on isn't built. The view answers on the broker host's loopback address; a hosted broker can serve it on its public origin with invites and passkeys. With OIDC sign-in, only people who can reach the broker host can approve connections, ratify terms or export their ledger.
- **Notification delivery.** The reference broker prints each notification and appends it to `outbox.jsonl`; it sends no email, SMS or Teams message yet (spec Section 12.5.1).
- **Retention.** `retention.ledger_days` is recorded, but nothing is purged.
- **Operator commands.** There are no commands to rotate the broker's signing keys or `ALP_KEYRING_KEY`, or to revoke every connection of one person or one client; a policy kill switch and `SIGHUP` do the latter today. When the identity provider stops accepting a person, only the connection being refreshed ends; that person's personal access tokens and web sessions aren't revoked with it.
- **Identity provider.** The broker authenticates to the identity provider with client secrets only; certificate (`private_key_jwt`) credentials aren't supported. Against a live Microsoft Entra tenant, no Conditional Access policy (sign-in frequency included) has been tried yet, nor group claims and the groups overage, a role change between refreshes, an address change or a re-created account, guests or a multi-tenant app: the sign-in was tested there once, on November 8, 2026, against a single-tenant Microsoft Entra ID (Free) tenant with test users, where sign-in, the tenant and object id binding, app roles in policy, a fresh sign-in for each approval and the re-check at each token refresh worked, and disabling a user ended their agent's connection at its next refresh ([SELF-HOST.md](SELF-HOST.md#tested-against-a-live-entra-tenant)). SCIM provisioning isn't built.
- **Further limits.** The limit between a person's own agents is set by an environment variable only (`ALP_OWN_AGENT_RATE_LIMIT`), with no policy setting. Per-agent shares of a person's limits and a per-token request budget on `/mcp` and `/rest` aren't built.
- **Client metadata documents.** The broker doesn't keep each connected client's last good client metadata document, so a refresh still depends on a live fetch.
- **Store and forward.** The reference retries a delivery inline for about 10 seconds, not on the schedule of spec Section 10.2 (30 seconds doubling to an hour until the envelope expires). A send that wasn't delivered shows only in its `alp_send` answer: `alp_thread` lists delivered messages only, where spec Section 10.2 has the delegate see the outcome.
- **Exports and operations.** The signed ledger export of spec Section 11.7, JSON logs with request ids, metrics, and container base images pinned by digest aren't built.
